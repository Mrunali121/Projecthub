Why it is built this way

Product thinking

The decisions behind the demo, and what changes at production scale.

Why this exists

A PM portfolio is usually documents. This project asks a different question: does the person understand how the product has to behave? What a Kanban board needs to feel responsive, what a sprint-planning screen must show in a real stand-up, and what makes a risk register get looked at instead of ignored.

Decisions and trade-offs

DecisionWhyTrade-off
No framework, no build stepAnyone can read the whole app file by file; deploys as a static site with zero config.No component reuse or structured state management; wouldn't scale to a large team product.
localStorage instead of a backendRuns on GitHub Pages with no server. One Store object is the only code touching storage, so swapping in an API is a one-file change.Data is per browser: no sync and no multi-user collaboration.
Mock authenticationLets a reviewer in instantly, and the login screen says plainly that it is a demo.Not a real security model.
Rule-based "AI"Honest and working; no API key exposed in a static site.Much simpler than a language model, and says so in the UI.
Fixed sprint capacity (28 points)Keeps the planning screen understandable.A real tool would compute capacity from availability data.
Hand-built SVG charts and GanttNo dependency that could disappear; shows the fundamentals.More code than using a library.

What a production version would change

  • Replace Store with calls to a real backend (for example Postgres with a REST or GraphQL API).
  • Replace mock auth with real sessions.
  • Add real-time collaboration (websockets or polling) so teammates see each other's changes.
  • Route the AI tool through a server-side proxy to a language model, with output checks.
  • Compute sprint capacity from team availability.
These were scope decisions, not gaps in knowledge. They match what a portfolio demo needs to prove, versus what a funded engineering team would build for production.
